# 케이스 스터디: LiteLLM 라우터가 fallback 전에 재시도 대기를 하던 문제

> provider 장애 때 fallback 응답이 요청마다 5초 넘게 늦던 문제를, 직접 만든 Kubernetes 플랫폼의 장애 실험으로 찾아서 LiteLLM(GitHub ★59k)에 수정 PR로 보냈습니다. 실제 OpenAI를 fallback으로 둔 측정에서 fallback 응답 중앙값은 5.53초에서 0.84초가 됐습니다.

| 항목 | 링크 |
|---|---|
| 수정 PR | [BerriAI/litellm#42450](https://github.com/BerriAI/litellm/pull/42450) (2026-09-22 기준 리뷰 대기, CI 통과, Greptile 5/5) |
| 같은 증상 이슈 | [BerriAI/litellm#40405](https://github.com/BerriAI/litellm/issues/40405)에 재현 결과 코멘트 |
| 추적 이슈 | [#20](https://github.com/RosieOh/RoundHouse/issues/20) |
| 발견 당시 기록 | [upstream-findings 5번](upstream-findings.md#5-router-single-deployment-groups-back-off-before-falling-back) |

## 1. 발견: 가용성은 지켰는데 지연이 10배

RoundHouse에서 `gpt-mock` 모델 그룹은 deployment가 하나이고, `claude-mock`으로 fallback하며, `num_retries: 2`입니다. mock provider가 요청의 80%에 500을 반환하게 하고 k6로 초당 6건을 4분간 보냈습니다.

| 설정 | 클라이언트 실패율 | 비스트리밍 p95 |
|---|---|---|
| 장애 없음 | 0% | 606ms |
| 장애, `num_retries: 2` | 0% | **6.57s** |
| 장애, `retry_policy`로 5xx 재시도 0 | 0% | 996ms |

fallback 덕분에 실패는 없었지만, 요청마다 몇 초씩 기다린 뒤에야 fallback으로 넘어갔습니다. 설정으로 우회할 수는 있었지만, 그러면 일시적인 5xx에서도 재시도 기회를 버리게 됩니다.

## 2. 원인: docstring과 구현이 달랐고, 이력에서 이유를 찾음

- `Router._time_to_sleep_before_retry`의 docstring은 "같은 그룹에 healthy deployment가 있거나 fallback이 있으면 즉시 재시도한다"고 적혀 있습니다. 하지만 구현은 앞 조건만 확인합니다
- deployment가 하나인 그룹은 지수 백오프(0.5초 × 2ⁿ, 최대 8초, jitter 최대 0.75초)를 탑니다. 대기는 첫 실패 뒤, 그리고 재시도가 실패할 때마다 들어갑니다. 마지막 재시도 뒤에도 대기하므로, fallback 전에 최소 3.5초가 쌓입니다
- `git log -S`로 추적해 보니, 2024-05-11 `3e6097d9f8`에서 "fallback이 있으면 즉시 재시도" 코드가 들어갔다가 **한 시간 뒤 `4d648a6d89`에서 설명 없이 빠졌습니다.** 당시 코드는 요청과 상관없이 라우터 전체의 fallback 목록만 봤습니다. 그래서 어느 그룹이든 fallback이 하나만 있으면 모든 그룹의 백오프가 꺼지는 문제가 있었고, 이것이 제거 이유였을 가능성이 큽니다
- 같은 증상의 이슈 #40405가 이미 있어서, 새 이슈 대신 그 이슈에 재현 결과를 남겼습니다. 같은 함수를 고치는 PR(#34408, #41261)은 `Retry-After`를 더 존중하는 반대 방향이라 겹치지 않았습니다

## 3. 해결: 무엇을 바꾸고 무엇을 바꾸지 않았나

| 선택지 | 판단 |
|---|---|
| fallback이 있으면 재시도 자체를 생략 | 일시적인 5xx에서 회복할 기회를 버림. 동작 변화가 큼 |
| **fallback이 있으면 재시도 사이의 대기만 생략** | 채택. docstring의 원래 의도와 같고, 재시도 횟수는 그대로 |
| 단일 deployment에 기본 cooldown | #40405가 제안한 방향이지만 설계 논의가 필요해서 이번 범위에서 제외 |

2024년 코드의 문제를 반복하지 않도록, **이 요청을 실제로 fallback이 받아 줄 수 있을 때만** 대기를 건너뜁니다. 판정은 LiteLLM의 fallback 디스패처와 같은 순서를 따릅니다.

1. 요청에서 fallback이 꺼져 있으면 해당 없음
2. 클라이언트가 요청에 담은 fallback 목록(문자열 목록이나 `{"model": ...}` 형식)
3. context window 에러와 content policy 에러는 전용 목록이 설정돼 있으면 그 목록만 봄(디스패처가 일반 목록으로 넘어가지 않기 때문)
4. 그 외에는 일반 fallback 목록(와일드카드와 `*` 포함). 이미 시도한 대상만 남았다면 해당 없음

## 4. 검증

- **테스트가 버그를 잡는지 거꾸로 확인**: 회귀 테스트는 `retry_after`를 최대 백오프(8초)로 두고 2초 제한으로 판정합니다. 백오프가 한 번만 일어나도 제한을 넘기 때문에, 타이밍 오차에 흔들리지 않습니다. 수정을 되돌리거나 2024년 방식(라우터 전체 목록)으로 바꾸면 해당 테스트가 실패하는 것을 확인했습니다
- **실제 provider로 측정**: PR 템플릿이 mock 결과를 증거로 받지 않습니다. 실제 provider의 장애는 원할 때 만들 수 없어서, 항상 500을 반환하는 20줄짜리 로컬 서버를 기본 모델로 두고 fallback은 실제 OpenAI `gpt-5.4-mini`로 호출했습니다. 수정 전은 merge base, 수정 후는 PR tip에서 각 10건씩 측정했습니다

| 케이스 | 수정 전 중앙값 | 수정 후 중앙값 | 장애 서버가 받은 시도 |
|---|---|---|---|
| 라우터 설정의 fallback | 5.53초 | 0.84초 | 양쪽 모두 30회 |
| 요청에 담긴 fallback | 5.42초 | 0.73초 | 양쪽 모두 30회 |

## 5. 리뷰 대응

- **자동 리뷰(Greptile) 4/5, 지적 2개**
  - 에러 종류별 전용 fallback 목록을 무시한다
  - 클라이언트 형식 fallback을 판정하지 못한다

  둘 다 타당한 지적이었습니다. 판정을 디스패처 순서에 맞게 다시 짜고, 두 경우를 재현하는 테스트를 추가했습니다. 재리뷰에서 5/5를 받았고, 남은 지적은 없습니다
- **CI 실패 2개**
  - `code-quality`: router.py의 모든 함수 이름이 테스트에 나와야 한다는 검사였습니다. 새 함수를 직접 호출하는 판정표 테스트를 추가했습니다
  - `proxy-infra`: PR의 기준 커밋이 main에서도 똑같이 실패하던 테스트였습니다. 최신 main으로 rebase해서 해소했습니다
- 커밋이 바뀔 때마다 PR 규칙대로 실제 provider 측정을 다시 했습니다

## 6. 한계와 다음 단계

- 장애 난 provider는 여전히 요청마다 `num_retries + 1`번 호출을 받습니다. 호출 자체를 막으려면 `allowed_fails`와 `cooldown_time`으로 cooldown을 걸어야 합니다. 그룹당 deployment를 2개 두는 구성과의 비교는 [#37](https://github.com/RosieOh/RoundHouse/issues/37)에서 합니다
- fallback이 없을 때 마지막 재시도 뒤의 대기는 그대로 남아 있어서, 에러 응답이 늦게 옵니다. [#30](https://github.com/RosieOh/RoundHouse/issues/30)에서 따로 다룹니다

## 7. 예상 질문

**왜 재시도를 없애지 않고 대기만 없앴나요?**
일시적인 5xx는 바로 다시 보내면 성공할 수 있어서 재시도 자체는 가치가 있습니다. 문제는 fallback이 기다리고 있는데 시간을 쓰는 대기였습니다. 대기만 없애면 동작 변화가 가장 작고 docstring의 의도와도 맞습니다.

**2024년 코드와 무엇이 다른가요?**
그때는 라우터 전체에 fallback이 하나라도 있으면 모든 요청의 대기를 없앴습니다. 이번에는 이 요청에서 디스패처가 실제로 쓸 fallback이 남아 있는지를 봅니다.

**타이밍에 의존하는 테스트는 불안정하지 않나요?**
백오프 최소값을 최대치(8초)로 올려서, "대기했다"와 "대기하지 않았다"의 차이를 수 초 단위로 벌렸습니다. 2초 제한은 정상 경로보다 훨씬 길고 백오프 한 번보다 훨씬 짧습니다.

**mock 없이 장애를 어떻게 재현했나요?**
장애 난 쪽만 로컬 500 서버로 두고, 사용자가 받는 응답(fallback)은 실제 provider로 받았습니다. 장애 서버가 받은 시도 수를 함께 세어서, 재시도 횟수는 그대로이고 대기만 사라졌다는 것을 보였습니다.

**리뷰에서 무엇을 배웠나요?**
"fallback이 있다"는 조건 하나에도 에러 종류와 요청 형식에 따른 분기가 여러 개 있었습니다. 판정 로직을 따로 만들지 않고 실제로 실행되는 코드(디스패처)의 순서를 그대로 옮기는 것이 안전하다는 것을 확인했습니다.
